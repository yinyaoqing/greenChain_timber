## 1. 開發方法與原則

**流程**：個人 Kanban（Backlog → Doing → Done），不開正式 Scrum 會議，改以「每日收工 15 分鐘自我 stand-up」記錄：今天完成、明天首件事、目前最大風險。記錄直接寫在 repo 的 `docs/engineering/devlog.md`，兼作 Demo 時的開發歷程證據。

**三條鐵律**

1. **垂直切片優先**：每週結束時系統必須「端到端可跑」到該週里程碑，寧可功能淺也不留半成品水平層。
2. **先醜後美**：W1–W3 一律不調 UI 細節，所有視覺打磨集中在 W4；避免個人開發最常見的「調 CSS 調掉半天」陷阱。
3. **每日可回退**：每天至少一個可運作的 commit 推上 GitHub；main 分支永遠保持可部署狀態。

**任務編號規則**：`T{週次}.{序號}`，例如 T1.3 = 第 1 週第 3 個任務。每個任務標注對應規格書條目、預估工時（h）與完成驗證方式（DoD）。

## 8. Git 與 CI/CD 約定

分支策略採簡化 trunk-based：日常直接小步 commit 進 `main`（個人開發，PR 開銷不划算），但**每週里程碑打 tag**（`m1-backend`、`m2-frontend`、`m3-chain`、`m4-release`）作為可回退錨點。Commit 訊息格式 `T1.4: 完成幾何正規化與雜湊`，任務編號可直接對照本計畫追進度。CI 於每次 push 跑 ruff + pytest + hardhat test；Vercel 自動部署 Preview，Render 綁 `main` 自動部署（W4 前 Render 先不建，避免免費額度空轉）（已收官，Render 已建置並上線，此句不再適用）。

**秘密管理紅線**：`MINTER_PRIVATE_KEY` 與所有連線字串只存在 Render/Vercel 環境變數與本機 `.env`（已列入 `.gitignore`）；repo 內放 `.env.example` 列出變數名稱但不含值。每次 commit 前 `git diff --staged` 自查一次。
